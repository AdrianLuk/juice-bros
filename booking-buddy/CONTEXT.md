# Booking Buddy

A friend-group pickleball scheduling app living under the Juice Bros platform. Lets people post open playing time, see friends' availability, and coordinate games without ad hoc chat polls or juggling separate facility-booking sites.

## Language

**User**:
A person with an account in Booking Buddy.
_Avoid_: member. (Player was reserved here pending a distinct concept — see Player, now split out below.)

**Username**:
The handle a User shares so friends can find them without giving out an email address — unique, lower-case, and safe to display. Assigned automatically at signup (derived from display name, or the email local part when there is none) so every User is discoverable without having to set one up; changeable afterwards.
_Avoid_: Handle, nickname (both fine in product copy; Username is the canonical term)

**Connection**:
A mutual, two-sided friendship between two Users, established when one sends a friend request and the other accepts. Required before either User can see the other's availability or invite them to a Slot.
_Avoid_: Friend (use as informal shorthand only), Follow, Follower (rejected model — connections are symmetric, not one-way)

**Connection Request Email**:
The email sent to the addressee the moment a pending friend request is created — any of the three paths that create one (the Friends-page request, the Invite Link "connect" button, the first signup through an Invite Link). Carries **Accept** and **Decline** links that work in one click straight from the inbox, with no sign-in: each is `/connect/<token>`, where the token is a single-use `connection_request_links` row minted by a database trigger on `connections` and burned on first use. The link's page only renders on GET — the accept/decline is a POST — so a mail prefetcher can't act on it. Session-less is a deliberate call (see [adr/0017-connection-request-email-is-session-less.md](docs/adr/0017-connection-request-email-is-session-less.md)): accepting only creates the Connection — though since [adr/0021-visibility-default-is-calendar.md](docs/adr/0021-visibility-default-is-calendar.md) that Connection opens `calendar` Visibility both ways by default, which the email's own copy states before the recipient accepts. Governed by its own opt-out, `notification_preferences.connection_request_email_enabled` — independent of the two Reminder toggles, and on by default. Reuses the Reminder delivery stack (Resend, `REMINDER_FROM_EMAIL`); a deploy with neither set simply sends nothing, the same fail-soft the Reminder job takes.
_Avoid_: Invite email (an Invite Link is a different thing — a cold-start link for people not yet on Booking Buddy; this email is only ever sent to an existing User who now has a request waiting)

**Connection Accepted Email**:
The follow-up to the Connection Request Email, sent to the original requester the moment their request is accepted — on either accept path (the signed-in Friends page, or the session-less `/connect/<token>` link). Plain notification, no action to take: it carries one link to the Friends page. Governed by its own opt-out, `notification_preferences.connection_accepted_email_enabled` — independent of `connection_request_email_enabled` and the two Reminder toggles, and on by default. Reuses the same Resend / `REMINDER_FROM_EMAIL` stack and the same fail-soft (no keys set → sends nothing).

**Friend Group**:
A named, user-owned collection of a User's own Connections (e.g. "Tuesday crew"), used to set a default visibility level for calendar/Slot access. Groups are private to their owner — one User's grouping of a friend has no effect on how that friend groups them back. Since [adr/0021-visibility-default-is-calendar.md](docs/adr/0021-visibility-default-is-calendar.md) a Group's visibility level only bites for a User who has lowered their `default_friend_visibility` below `calendar` — for everyone else the default already grants everything a Group could add. Groups are kept for organising the people you play with (and BB-1's recurring games), and are reached from an "advanced" link on the Friends page rather than the primary nav.

**Visibility**:
How much of a User's calendar/Slot data a given Connection can see. Four levels: `none` (nothing), `slots` (only the Slots the owner shares with them), `open_time` (only the owner's Availability Windows, no Slots), `calendar` (both Slots and Availability Windows). Not a total order — `slots` and `open_time` are independent, incomparable grants; `calendar` is both of them together, `none` is neither. Resolved per friend as: an explicit per-friend override always wins if set; otherwise, every Group the friend is in contributes its grants, unioned on top of the owner's **default Visibility** — a per-User setting (`profiles.default_friend_visibility`) that is `calendar` by default, so a freshly accepted Connection with no Group and no override sees the owner's games and Availability Windows straight away. Adding a friend to a more-open Group can only expand what they see, never silently restrict it — an override is the only way to close one person off (below the default or the Group they are in). Lowering the default is a live change: it moves every friend still on it. See [adr/0007-visibility-is-a-lattice-not-a-scale.md](docs/adr/0007-visibility-is-a-lattice-not-a-scale.md) for the lattice and [adr/0021-visibility-default-is-calendar.md](docs/adr/0021-visibility-default-is-calendar.md) for the default.

The picker labels `open_time` "Just my availability" and `calendar` "Slots and my availability" — the enum values (`open_time`, and the `has_open_time_visibility` / `open_time_visible_owners` DB objects) keep their names; only the user-facing copy changed when the Availability page was renamed.

**Place**:
A real-world pickleball facility as Google Maps knows it — "PicklePlex Downsview", "Vaughan Pickleball" — identified by its Google `place_id`. Not something Booking Buddy owns or maintains: the list of Places is Google's, and the app only ever holds the ones its Users have actually picked. Facts about a Place (display name, address, coordinates) are cached server-side and refreshed, never authored here. See [adr/0005-orgs-identified-by-google-place-id.md](docs/adr/0005-orgs-identified-by-google-place-id.md).

**Org**:
One User's record of playing at a Place — the thing their Bookings hang off. A single User can have Bookings across multiple Orgs, and two Users who play at the same Place have separate Orgs pointing at the same `place_id`, which is what lets anything cross-User join them up. Where a venue isn't in Google Maps (a community-centre gym, a private court), an Org carries a hand-typed name instead and has no Place; it is one or the other, never both. A place-backed Org cannot be renamed — its name is the Place's, so everyone sees the same one.

Bookings under an Org are still entered by hand: Google supplies the venue's identity, not its reservations (ADR 0002 stands). An Org may also carry a Booking Window, driving the Booking Reminder. One Org per owner may be marked the **default facility**, pre-selecting it in the Booking form's picker instead of forcing an explicit pick every time; picking a different Org as default simply moves the mark, there is no "unset." The very first Org a User ever adds is marked default automatically — a database trigger, not app bookkeeping, so it holds regardless of which creation path added it.
_Avoid_: Club (use Org as the canonical term internally, matching how platforms like CourtReserve model it). Note that an Org is a User's *record*, not the venue itself — the venue is a Place.

Product copy is the deliberate exception: the Orgs page reads "Facilities" to non-technical Users, since "Org" means nothing to them and "Club" is wrong for a chunk of real entries — Toronto's own pickleball scene splits between venues that brand themselves a Club (Pickleplex Social Club, Vaughan Pickleball Club) and public Community/Recreation Centres, which explicitly aren't clubs (no membership, city-run). "Facility" is the umbrella term that's accurate for both, so it's what the UI says even though the entity underneath is still an Org.

**Onboarding**:
A modal shown on the Booking Buddy dashboard while the signed-in User has **no Booking and no Slot** — the point before which they've gotten nothing back from the app. Not gated on account age or a "first login" flag; it's the live "no Booking and no Slot" check, so it resurfaces for any such User (new signup or long-standing account alike) and stops for good the moment either exists — a booking-only User who never wants Slots isn't chased about facilities forever once they've logged one. Never a hard gate: dismissible at any step, and a dismissal snoozes it for ~7 days (a `localStorage` timestamp, per browser) so it nudges without nagging rather than reappearing on the very next load. The Booking-requires-an-Org enforcement is unchanged and lives elsewhere (the database constraint, the Log-a-Booking fallback prompt); Onboarding is a convenience on top, not a new gate.

One modal, branched on a modal-local **intent** choice (never persisted — a per-User "primary intent" for later tailoring is a follow-up): "track my court bookings" walks Add-a-Facility, then **bringing that facility's reservations over**: the Calendar Feed field leads (one pasted link against typing a booking in, and it keeps paying afterwards), with Log-a-Booking offered plainly beneath it for the community-centre gyms and private courts CourtReserve doesn't run, and a way back to the feed from the hand path. Saving a feed ends the branch on a handoff to the Bookings page with the sync already running (`?sync=1`) — the reservations on a feed are a review, not Bookings yet, so the modal says so rather than rebuilding the review list inside itself. "get my group on a time" posts a Slot (pre-filled to next Monday 8-10pm, no facility needed) then shares it. Gender is surfaced in the "coordinate" branch only, collapsed, where a gender-aware Slot division is the reason to ask (see [adr/0012-onboarding-surfaces-gender-proactively.md](docs/adr/0012-onboarding-surfaces-gender-proactively.md)). Every step past the choice keeps a persistent "add the people you play with" footer (friend search) — the one universal onboarding goal, since a Connection is the precondition for shared availability and Slot invites. Reuses the Facilities/Bookings/Slots pages' own forms unchanged. See [adr/0015-onboarding-intent-branch.md](docs/adr/0015-onboarding-intent-branch.md).
_Avoid_: Onboarding flow, Setup wizard (this is one modal, not a multi-page flow or a persisted checklist)

**Booking**:
A single court reservation at a specific Org, owned by a User, with a date/time and an optional court label (not every facility labels its courts, and not every User bothers to note one down) — mirrors one reservation record as it exists on the facility's own platform (e.g. one CourtReserve reservation = one Booking). Entered manually by the User; there is no "unconfirmed" or "intended" state — a Booking represents a reservation that exists. Carries its own format — doubles or singles, defaulting to doubles — which is what a court's own share of Capacity is derived from (see Capacity), and its own list of Players (see Player) — who was actually there, separate from any Slot's Responses/Guests. Also carries an optional, free-text name (issue #94) — a label the User gives the session itself ("Tuesday night rally"), independent of the court label and never derived from Format; rendered above the facility name wherever one is shown on the owner's own dashboard, and not backfilled onto Bookings logged before it existed. Separately carries an optional, free-text notes field — for detail that doesn't belong in the name itself (court instructions, gear reminders, who's flaky), shown only in the Booking's own detail view rather than on the compact list/dashboard rows where name already serves as the title. A gathering spanning multiple courts (e.g. an 8-person game held as two separate court reservations for the same window) is multiple Bookings attached to one Slot, not multiple Slots. A session that runs past midnight (a 9pm–midnight or 10pm–1am game) is a single Booking spanning one calendar-day boundary — the form takes a start date, a start time, and an end time, and reads an end at or before the start as landing on the next day, storing the end instant there; spans across more than one midnight aren't offered. Along with any confirmed Slot built on it, a Booking is the authoritative source of busy time in a User's Availability — see Availability Window.

Editable in full — Org, court label, name, date/time, format, and Players — with no restriction tied to whether the Booking is already in the past: the same "no unconfirmed state" reasoning that rules out a Booking ever being partially real also means editing one has nothing to protect against that creating one doesn't already allow. (The past-date guard on the underlying row is deliberately insert-only, precisely so an edit is never blocked by it.)

**Player**:
Someone recorded as having played in a Booking — a name, plus an optional link to the Connection it matched. Entered by hand when logging a Booking (a single comma-separated list, split into names), or carried straight through from a CourtReserve confirmation or reservation-update email's own "Player(s)" section when an Import Candidate is confirmed — either way, unedited names land on the Booking as-is; a wrong parsed name is fixed via Edit Booking afterward rather than on the review screen itself.

The Connection link is resolved once, at the moment a Player is added — exact case-insensitive match against the User's Connections — and then stored, not recomputed later: renaming a Connection or a Player's own name never silently changes what a past Booking shows. A name matching more than one Connection (display names aren't unique — see Connection) is stored unlinked rather than guessed at, since a wrong guess would now be a permanent misattribution instead of a throwaway display hint. If a linked Connection later ends, the link clears but the name stays — a Booking is a historical record and doesn't lose data because a friendship did.

Entirely independent of a Slot's Responses/Guests, even when the Booking is attached to one — Players describe who was actually on the court (what the reservation itself says), Responses/Guests describe who said they'd come (a poll that can predate any court being booked and can include no-shows). The two lists are never reconciled, pre-filled from each other, or expected to agree. Unconstrained by the Booking's format — a doubles Booking can log more than 4 Players (rotation/subs are real), and the same name can appear twice (two different people can share one).
_Avoid_: Guest (a Slot RSVP identity — name-only, never links to a Connection, and belongs to a different list entirely; see above)

**Mailbox Link**:
A User's account-level OAuth grant to their own email inbox (Gmail, or Outlook/Hotmail — spec #280; both connect and sync are live for either provider), used only to search for CourtReserve confirmation/cancellation mail when the User triggers a sync. One Link per User, carrying which `provider` it belongs to; not tied to any single Org — one Link covers a User's Bookings across every facility. A Link can lapse and need the User to re-establish it: a Gmail Link expires periodically under Google's Testing-mode verification status; a Microsoft Link when its refresh token or the app's client secret lapses. See [adr/0009-email-sync-via-gmail-oauth.md](docs/adr/0009-email-sync-via-gmail-oauth.md), extended for Microsoft by [adr/0018-email-sync-microsoft-provider.md](docs/adr/0018-email-sync-microsoft-provider.md).
_Avoid_: Connection (already means a two-sided friendship between Users — do not reuse for this), Gmail Connection

**Calendar Feed**:
A User's standing grant to a second external source of Booking data, sibling to the Mailbox Link: where a Mailbox Link is one account-wide OAuth grant to an inbox, a Calendar Feed is a per-Org pasted URL — the member's own CourtReserve club calendar feed (`.ics`), set on a Facility's edit form or on the Onboarding modal's track branch, which leads with it. CourtReserve issues one feed per club, so a feed's scope already equals an Org's; there is no account-wide feed. The URL carries a private member token and is stored encrypted at rest (`orgs.calendar_feed_url`, same key and utility as the Mailbox Link's refresh token — see [adr/0019-calendar-feed-second-import-source.md](docs/adr/0019-calendar-feed-second-import-source.md)). Available to every User — not gated on the email-sync allowlist, which only exists to manage Google's Testing-mode cap. Fetched on demand when the User hits "Sync bookings" (the one action that runs both this and the Mailbox Link, unified in #336 — no cron in v1); a broken, unreachable, or non-CourtReserve URL reports a clear per-Facility error rather than failing silently, and one feed failing never stops the others syncing or the email source.

Each sync diffs the fresh fetch against what the feed showed last time, tracked in `org_feed_events` — one mutable row per seen VEVENT UID per feed (`last_seen_at` bumped every sync), each `pending` / `imported` / `dismissed` and carrying the `booking_id` it settled to when imported. A future-dated event becomes a confirmation-shaped Import Candidate; a reservation that has **vanished from the feed** (or now carries a cancelled status) and matches a logged future Booking becomes a cancellation candidate — whichever way that Booking was created, since every parsed event is auto-linked to a matching Booking on each sync. Four safety rails stop a narrowed, broken, or swapped feed reading as mass cancellation: a failed or empty fetch runs no diff at all; a past-dated event is skipped, never flagged; an explicit cancelled status is always honoured; and a sync that would flag an implausible share of an Org's Bookings warns "this feed looks wrong" instead. Clearing the URL from a Facility also deletes that Org's `org_feed_events` rows, so re-pasting later starts from a clean slate. Each sync run also prunes rows whose reservation and last sighting are both 90 days past (issue #452) — nothing reads one, since a past-dated event is dropped before the table is consulted and a vanished UID is only flagged while its start is still in the future. The prune keys on `last_seen_at` as well as `starts_at` so that a settled row whose `starts_at` was never readable isn't forgotten and its event offered again. It does move one thing: the count of rows is what the fourth rail measures its "implausible share" against, and an unpruned table made that share unreachable on an old Facility. Bounded, the rail fires as designed — on a quiet Facility, cancelling two of three upcoming reservations at once now shows the "this feed looks wrong" warning rather than offering both as cancellation candidates, and those Bookings come off by hand. The 90-day retention is what makes that arrive gradually.
_Avoid_: iCal Feed, ICS Feed, Feed Link, Calendar Subscription, Calendar Sync (all describe the same thing; Calendar Feed is the canonical term, "calendar feed" / "Import from a calendar feed" the product copy). Not a Mailbox Link (that is the inbox grant), and not a Connection.

**Import Candidate**:
A parsed CourtReserve confirmation, cancellation, or reservation-update email, matched against the User's Orgs and existing Bookings but not yet applied — shown on a review screen for the User to confirm before it becomes, removes, or edits a real Booking. Never a Booking itself; discarding one has no effect on any Booking. Skipped automatically, without ever becoming a candidate the User sees, when it's a confirmation for a date/time that's already passed or that duplicates an existing Booking (same Org, court, and date/time). A reservation-update email that arrives alongside its own confirmation in the same sync nets into a single confirmation-shaped candidate rather than becoming a separate one; an update with no in-batch confirmation to net against is matched against an already-logged Booking (Org + date/start-time, not court, so a real court change is still applicable) instead — confirming it rewrites that Booking's slot, format, court and Player(s) (issue #458; an update email listing no Player(s) at all leaves the Booking's own list alone, since that is the facility saying nothing rather than "nobody"), and the card shows a before/after of exactly that — matching on a start time says nothing about whether the End, the court or the Players are about to change. An update that moved its **start time** matches nothing under that key — the very case the exact-match rule was blindest to, since the Booking it refers to is usually sitting right there on the same day and court. So rather than reporting it missing, the review offers the Bookings at that facility on that calendar day as **suggested matches**, best first (the same court and an overlapping time ahead of one sharing neither, nearest start time breaking ties, at most three), each shown with a before/after of exactly what applying the update would change to it. The User confirms one; nothing is ever applied on the strength of a suggestion alone, which is how the "refuse to guess" rule survives being widened. A Booking another candidate in the same batch already matched exactly is never offered as a maybe, and only when nothing at all is on file that day does the "no matching booking found" notice stand on its own. The whole parse → net → match → filter → order pipeline that turns a batch of raw CourtReserve emails into these candidates is `reviewCourtReserveEmails` (`src/lib/booking-buddy/email-sync-review.ts`), a pure function; `syncFromEmail` is only the Gmail/Supabase I/O around it. In code all three are one `kind`-tagged `ReviewItem` union (that same module), returned as a single flat list the review screen groups back by kind — not three separate lists.

Confirming an import or applying an update records the email as settled (a `processed_messages` row) so later syncs skip it — but that record is tied to the Booking it produced, so **deleting that Booking from the Bookings page later clears the record automatically and the next sync re-offers the email** (issue #286; the realistic path back to a deleted confirmed Booking is recovery, and a deliberate delete just means dismissing the re-offered email once). Confirming a *cancellation* also deletes the matched Booking, and it settles every source that reservation came from, not only the one that reported the cancellation (issue #609): each email tied to the Booking is re-recorded as cancelled, so its confirmation stays suppressed, and the feed event tied to it is marked dismissed, so a feed still listing the event does not offer it again as an import. A cancelled reservation is not something to re-import, from either source. Dismissing an email suppresses it for good.

The review screen has to say that it *is* a review, because it does not look like one (issue #464). A sync that finds anything renders the User's genuine reservations in a list, under a section whose own copy promised to "pull in" those reservations, which reads as the job being done — and the button that actually saved one said "Confirm", the one button in the section that named no outcome next to a "Remove booking" and an "Apply update". A first time User took the list for her calendar and never pressed it. So the cards now arrive under a **"Review N reservations"** heading and the line "Nothing here is saved yet. Choose Add to my bookings on the ones you want to keep. Booking Buddy never changes your reservation at the facility." — state, then the instruction naming the button, then the sentence that also answers what Dismiss does (the other thing a real reservation on screen makes frightening). The middle sentence renders only while at least one card on screen carries that button, since a review list holding nothing but cancellations and updates has none, and pointing that User at a control they cannot see would be worse than saying nothing; the import button on all three import-shaped cards reads **"Add to my bookings"** and sits in one row beside its Dismiss, rather than a layout apart from it; and because a settled card is dropped from the query cache and simply vanishes — into a Booked list that sits *above* this section, off-screen on a phone — the section keeps a running **tally** of what this sync settled ("Added 2 bookings.", "Skipped 1.") with a link to Booked. The tally starts over on each sync, and while it stands the "No new bookings found." empty state is held back: clearing the last card is not the sync having turned up nothing.

When a User has **both** import sources configured for one facility (a Mailbox Link and a Calendar Feed), the same reservation arrives from each — an email candidate carrying the Player(s), a feed candidate carrying none — and the review screen consolidates the pair into a **single card** rather than showing it twice (`mergeImportCandidates`, `src/lib/booking-buddy/merge-import-candidates.ts`; ADR 0020). The two are matched on Org + date + start time, deliberately *not* court (the sources disagree on court text — the feed's is thinner); the merged card keeps the Player(s), name and fuller court label from the email side and the feed-event identity from the feed side. Confirming it once creates one Booking and settles both sources (a `processed_messages` row *and* an `imported` `org_feed_events` row); dismissing settles both. An email candidate whose facility didn't match an Org is left as its own card (no Org to match on), as is either side when more than one candidate shares a slot — the same "refuse to guess" rule the cancellation match uses.

That consolidation only fires when both candidates land in the *same* sync run, so settling one source has to reach the other on its own. A **confirmed** candidate does that by itself: it leaves a Booking behind, and each source recognises a reservation already on file by Org + date + start time + court *number* rather than by court text, so the email's "#9 - Hard" and the feed's "#9" read as one reservation (issue #432). A **dismissed** candidate leaves no Booking to recognise, so the slot itself is recorded (`dismissed_reservations` — Org, date, start time, and the dismissing source's own court text) and both reviews skip a candidate matching one, on the same identity (issue #437). That changes what a dismissal means: it was "never show me this message again" / "never show me this feed event again", and it becomes **"never offer me this slot again", from either source**. The cost is a cancel-and-rebook of the same slot — a genuinely new reservation, which used to arrive with a fresh message id and a fresh VEVENT UID and be offered, and is now dropped by both sources. A slot is the only key the two sources share, and suppressing only the counterpart source wouldn't help (a rebook regenerates both sides), so the drop is **said out loud and reversible** instead (issue #444): a sync that drops candidates this way returns them (a **suppressed reservation**, the code's own term, on both reviews' results), the review screen lists them under "N bookings were skipped because you dismissed them before", and **"Offer this again"** deletes the dismissal so both sources offer that slot again. That list can't tell a rebook from the ordinary counterpart of a dismissal made on the *other* source, since both are a candidate with no decision recorded on its own side for a slot the User said no to, so it reports both rather than guess and lose a rebook again. It deletes every `dismissed_reservations` row matching the slot, since both sources record their own with their own court text; it deliberately leaves the source-side `processed_messages` / `org_feed_events` rows standing, so it is not a replay of the message or feed event the User said no to — only the *slot* stops being suppressed. Dismissing a *cancellation* or update candidate records no slot: "keep booking" means keep the Booking, not "I don't want this reservation". A dismissal is never rewritten in place, and it never touches a Booking either way. Rows for slots that have already been and gone are pruned by each sync (issue #447) — a past-dated candidate is dropped before the dismissal check ever runs, so such a row suppresses nothing; the prune keeps a day of slack behind UTC so that a slot still live in the last time zone on Earth is never cleared early.
_Avoid_: Pending Booking, Draft Booking (a Booking has no unconfirmed state — see [adr/0009-email-sync-via-gmail-oauth.md](docs/adr/0009-email-sync-via-gmail-oauth.md))

**Settle**:
To take an Import Candidate to its final state for every source it came from. Confirming one settles it (it becomes, removes or edits a Booking), and so does dismissing one. Either way the record for each source the candidate carries is written: a `processed_messages` row for an email, an `org_feed_events` row for a Calendar Feed event, and the slot in `dismissed_reservations` when a new-reservation candidate is dismissed. That record is what stops the next sync offering the candidate again. A merged card settles both its sources at once. Confirming a cancellation from either source settles both: the emails tied to the Booking are recorded cancelled and the feed event tied to it is marked dismissed, so neither source offers the reservation again (issue #609). In code one module owns settling (issue #606, `import-candidate-settlement.ts`): `confirmCandidate` and `dismissCandidate`, behind the `confirmImportCandidate` and `dismissImportCandidate` Server Actions, which only check the session and email sync entitlement, call the module, and refresh the page.
_Avoid_: Resolve, Process (both too vague to say every source was written); Apply (that is the "Apply update" button, one way to settle an update candidate)

**Availability Window**:
A User's own dated declaration of being `looking` (looking to play) or `busy` over a specific time span (start/end timestamps, free to cross day boundaries — a whole week off is one window, not seven). Shown to Connections with `open_time`- or `calendar`-level Visibility. Entirely informational: an Availability Window never blocks, cancels, or auto-declines a Slot invite or Response — it only signals a User's own read of their schedule. `looking` is an active "invite me to a game" signal, deliberately distinct from `busy` and from silence (a moment with no window at all, which reads as free-but-not-soliciting); it was renamed from `open` because that old name did nothing "no window" didn't already do (issue #229). Independent of Bookings — a User can declare one without ever having reserved a court, which is the point: unlike a Booking, it costs nothing to say "I'm looking to play this weekend" or "I'm booked solid this week" without touching whatever facility platform the actual reservation lives on.

Resolving what a User's calendar shows at a given moment, in order: a Booking or a confirmed Slot (one with a Booking attached) always wins and reads as busy, regardless of any Availability Window declared over the same span; otherwise, the most recently *created* Availability Window covering that moment wins — editing an existing window's own time range or type later doesn't change its place in that order; otherwise the moment is unspecified, shown as neither. Availability Windows carry no uniqueness or overlap constraint (see [adr/0006-availability-layered-precedence.md](docs/adr/0006-availability-layered-precedence.md)), so deleting one reveals whichever older window, if any, still covers that span, rather than leaving a gap.

A `looking` window is consumed in three places (issue #230): its calendar block gets a warm primary tint (an opening, not the neutral grey a bare not-busy stretch would get); the Games page carries a **"Friends looking to play"** section — a flat, soonest-first list of every upcoming `looking` window a friend has shared with the viewer, each with a "Propose a game" deep-link prefilled to it (`listFriendsLookingToPlay`, `actions/looking.ts`; **not an entity**, gated the same `open_time` way Find a time is); and "Find a time" flags a shared-free block with a "… is looking to play" line when a picked friend has a `looking` window over it, without changing which blocks are shown.

Product copy is the deliberate exception, the same way the Orgs page reads "Facilities": the page's nav pill and title are **"Availability"** (see [adr/0016-two-tier-app-navigation.md](docs/adr/0016-two-tier-app-navigation.md); the old "Open time" mislabelled a list that holds `busy` windows too), the `looking` type reads **"Looking to play"** (**"Looking"** on a compact calendar block), the list of a User's own Windows — on that page and in the dashboard sidebar — is headed **"Your availability blocks"**, and the create section is **"Block off time"**. The `open` → `looking` rename runs to the `availability_type` enum value itself (migration `20260831140000`).
_Avoid_: Free time, Schedule. "Looking" / "Looking to play" is the product term for the type; "Availability" is now the page name and the informal feature name (Availability Window stays canonical for the entity). "block off" / "availability blocks" appear in product copy (the create section, the list heading) — that's deliberate.

**Find a time**:
A read-only view (product label "Find a time", route `/booking-buddy/overlap`) that intersects the viewer's and a chosen set of friends' availability over a week/month range and surfaces the stretches they are *all* free, each with a one-click "Propose a game" deep-link into the Games form (date + start time prefilled). **Not an entity** — no table, no stored state; pure aggregation (`resolveCommonOpenSegments`, `src/lib/booking-buddy/availability.ts`) over data the existing Visibility gates already expose. "Free" here means *not busy*: a moment counts unless a Booking/confirmed Slot covers it or the Availability Window winning ADR 0006 precedence there is `busy` — an "unspecified" moment (no window at all) counts as free, so a friend who has declared nothing is treated as available rather than unknown. A friend only appears in the picker if their resolved Visibility currently grants the viewer `open_time` (the same `friend_visible_bookings` / `open_time_visible_owners` gate the one-friend calendar uses); the view never widens what a friend exposes. Serves the coordinate-a-time intent (#176), issue #195.
_Avoid_: Overlap (fine informally; "Find a time" is the product term)

**Slot**:
The friend-facing unit that Connections see and respond to. A Slot can exist with zero Bookings attached — a bare proposal ("Saturday 9am, who's in?") used to gauge interest before anyone reserves a court, replacing the WhatsApp "who can make X date, yes or no" poll — and later have one or more Bookings attached once a court is actually reserved, becoming a confirmed Slot with real capacity. It's the same underlying record throughout: no separate "Poll" or "Event" entity, and attaching a Booking doesn't change its identity. Org/court is optional at creation for this reason. A proposed window that runs past midnight (a 10pm–1am game) is read the same way a Booking's is — an end time at or before the start lands on the next day — and spans across more than one midnight aren't offered.

Also carries an optional, free-text notes field, set at posting time or added afterward — the only field on an already-posted Slot editable outside the narrow `rotation_buffer`/Intended Org pattern, since the rest of a Slot's proposal (date/time, division) is fixed once posted. Shown only on the Slot's own detail page, not the Slots list.
_Avoid_: Event, Poll (informal shorthand for "a Slot with no Booking yet" is fine in conversation, but not a separate modeled entity), Session

Product copy is the deliberate exception, the same way the Orgs page reads "Facilities": the app's UI calls a Slot a **"Game"** — "Your games", "Post a game", "Delete game", the "Games" nav label under the Plan section (see [adr/0016-two-tier-app-navigation.md](docs/adr/0016-two-tier-app-navigation.md)) — because "Slot" is jargon a new user has to decode. The entity underneath is still a Slot: the database, all code, the `bb_first_slot` analytics event, and the `/booking-buddy/slots` URL are unchanged. **Slot Link** keeps its own name in the UI (it's a proper-noun feature, and renaming it would ripple into the guest-RSVP flow), and so does the **Visibility** copy that grants access to "Slots".

**Response**:
A Connection's (or Guest's) explicit yes/no/maybe answer to a Slot, replacing the implicit "silence means no" join model. Can be given whether or not the Slot has a Booking attached yet. A "yes" is always accepted — no organizer approval, and no block once Capacity is reached; going past it produces an over-capacity signal for the organizer, not a refusal (see Capacity, ADR 0001). Before a Booking exists there is no Capacity at all, so any number of "yes" Responses can accrue while gauging interest. "Maybe" never counts towards Capacity.
_Avoid_: RSVP (used informally in product copy), Join, Vote

**Capacity**:
The effective ceiling on "yes" Responses for a Slot: the base capacity derived from its attached Bookings' own court capacities, plus an optional rotation buffer the organizer can configure per Slot to allow for substitutions (e.g. a doubles court with a buffer of 2 supports up to 6 "yes" Responses, expecting some rotation in and out). Each Booking carries its own format — doubles (4) or singles (2), defaulting to doubles — so Capacity sums per attached court rather than assuming every court is the same (see [adr/0008-court-capacity-is-per-booking-data.md](docs/adr/0008-court-capacity-is-per-booking-data.md)). A Slot with no Bookings has no Capacity at all, which is not the same as a Capacity of zero: there is nothing to fill yet. "Yes" Responses beyond Capacity aren't blocked — the organizer sees an over-capacity signal to resolve manually (e.g. book another court, or read it as expected rotation/drilling rather than an actual overbook), same as an unbuffered overflow. Capacity is never stored; it is derived from the attached Bookings' formats and the buffer each time it's read.

**Reminder**:
An automated notification sent to Users with a "yes" Response on a confirmed Slot (one with a Booking attached — a bare proposal has nothing concrete to remind anyone about), at a time before the Slot's start configurable per Slot. Not sent to Guests in v1. Governed by its own opt-in preference, independent of the Booking Reminder's. Which sends actually go out on a given cron run is decided by `planAttendeeReminderRun` (`src/lib/booking-buddy/reminder-run.ts`), a pure function; the `send-reminders` route is only the fetch + delivery around it.
_Avoid_: confusing with Booking Reminder — this one is for attendees of a confirmed game; that one is for the organizer of a still-unbooked one.

**Booking Window**:
A facility's own rule for how far in advance it opens court reservations — captured per Org as an optional lead time (days before play) and time of day, in the facility's own time zone. Not discovered automatically; the User sets it once, from what they know of the facility's own booking platform (e.g. CourtReserve), and it's reused for every Slot pointed at that Org. An Org with no Booking Window set simply never produces a Booking Reminder.

**Booking Reminder**:
An automated notification sent to a Slot's organizer once its intended Org's Booking Window opens — a nudge to go actually reserve a court before it fills up. Only sent while the Slot still has no Booking attached (once one is, there's nothing left to remind the organizer to do) and to the organizer alone, never to attendees or Guests. Governed by its own opt-in preference, independent of the plain Reminder's — someone may want one without the other. Which sends go out on a given cron run is decided by `planBookingWindowReminderRun` (`src/lib/booking-buddy/reminder-run.ts`); the `send-booking-window-reminders` route is only the fetch + delivery.

**Intended Org**:
The organizer's own hint, on a still-bare-proposal Slot, at which Org they plan to book at — what a Booking Reminder is computed against. Not a reservation and not touched by attaching a real Booking; a bare-proposal Slot has no Org otherwise, since that only ever arrives via an actual Booking. Its resolved display name is also snapshotted onto the Slot (`slots.intended_org_name`, the same friend-visible-snapshot trick `slot_bookings.org_name` uses for a booked court) so that a bare proposal still names its facility in the Game title, for the organizer and for a friend who can't read the owner-only `orgs` table.

**Slot Link**:
A unique, shareable URL generated for a single Slot. Anyone holding the link can view that Slot's preview and RSVP, regardless of Connection status — it does not expose the organizer's broader calendar, only the one Slot it was generated for. The preview shows the same title a signed-in viewer sees, facility included (the booked court's, or the Intended Org for a bare proposal) — read off the friend-visible `slot_bookings.org_name`/`slots.intended_org_name` snapshots, so `orgs`/`bookings` stay closed even to this session-less caller.

**Invite Link**:
A User's own personal, shareable URL — `/booking-buddy/join/<token>`, where the token is a stable-but-rotatable `profiles.invite_token` assigned automatically at signup. Its purpose is the cold start: every other way to connect (`search_users`) only finds people who already have an account, so a new User whose friends aren't on Booking Buddy yet has no way in. Opening the link resolves to a pending friend request back to the owner — never an accepted Connection, so the mutual-accept model (see Connection) is untouched. A signed-out visitor sees a "<Name> invited you" landing and is routed through normal sign-in/sign-up with the token carried across the round trip (a short-lived cookie); on the first signup through it, the request is auto-created. A signed-in visitor gets an explicit "send request" button, or a friendly no-op if already connected / it's their own link. Rotating the token invalidates the old URL, cutting off a link shared too widely. One token per User, no history — not to be confused with a Slot Link (one per Slot, Guest-facing, RSVP-only).
_Avoid_: Referral link, Invite code (it's a link, and it carries identity, not a discount)

**Guest**:
Someone who RSVPs to a Slot via its Slot Link without holding a Booking Buddy account or being a Connection of the organizer. Identified by name only. RSVPing as a Guest does not create a Connection — becoming friends in the app is a separate, deliberate action.
_Avoid_: Player (a Booking's own record of who was on the court, which can link to a Connection and belongs to a different list entirely — see Player)

**Standing Game**:
An organizer's own template for a game that repeats ("Tuesday 8pm, every week") which posts ordinary Slots on its own, each one ahead of time: a week before the game, or earlier when its Intended Org's Booking Window opens sooner (the window's lead plus one day), so the Booking Reminder still has a Slot to fire for (which can mean two upcoming Slots from one Standing Game at once). Its first Slot is posted the moment it is created. It repeats weekly on one weekday at one time and nothing else: a group that plays Tuesdays and Thursdays has two Standing Games. It is not a Slot and is never seen by Connections or Guests: friends only ever see the Slots it posts (marked with the day it repeats on, "Every Tuesday", so they can tell it is a regular game), and each of those is a plain Slot in every respect (Responses, Capacity, Reminders, Slot Link, Bookings). Recurrence lives on the Standing Game alone, so nothing that reads Slots has to know a Slot came from one (see [adr/0023-standing-game-posts-plain-slots.md](docs/adr/0023-standing-game-posts-plain-slots.md)).

In the code (issue #577): the template is a `standing_games` row (weekday 0 = Sunday, start and end hour, an IANA time zone taken from the Intended Org or the Toronto fallback, division, Intended Org, notes, rotation buffer, reminder offset, `ended_at`), owner-only under RLS. Every week it has dealt with is a `standing_game_weeks` row, unique on (Standing Game, game date), which is what makes posting idempotent and outlives the Slot so a week is never posted twice. A posted Slot carries a nullable `slots.standing_game_id` for the UI alone (the chip, the next game); no policy reads it, and the chip is computed from the Slot's own date so a friend never needs the template. Posting goes through one SQL function, `post_standing_game_week`, which records the week and inserts the Slot in one transaction, building its instants from a wall-clock string and the zone the way `createSlot` does, so 8pm stays 8pm across daylight saving. Which weeks are due is `dueStandingGameWeeks` / `planStandingGamePostingRun` (`src/lib/booking-buddy/standing-games.ts`), pure. Every path that posts a week (the daily `post-standing-game-weeks` cron route, the creation action, putting a skipped week back on) goes through `postDueWeeks` (`standing-game-posting.ts`), which plans, posts, fires the week-posted Funnel Event and sends the Weekly Invites.

In product copy it is a **"weekly game"**: "Repeats weekly" on the Post a game form, a **"Weekly games"** section above "Your games" (one row per live Standing Game: its day and hours, facility, and next posted game), and the Standing Game's own page (`/booking-buddy/slots/weekly/<id>`) where it is edited and ended.

An organizer can also start one from a game they already posted: **"Make this weekly"** on their own one-off Slot's page (not on a Slot a Standing Game posted, not on a friend's) opens Post a game with "Repeats weekly" ticked and every field filled from that Slot: its weekday and hours on its own clock, division, Intended Org, notes, rotation buffer and reminder offset, with the Users who answered yes ticked as Regulars. The original Slot is left alone and is never adopted: it stays a plain one-off Slot, with no "Every Tuesday" chip. While it hasn't started, the new Standing Game treats its date as already covered and starts posting from the following week, so there is never a second game that day and nobody gets a Weekly Invite for one (Adrian's call, 2026-10-06). The covered date is not a skip and never shows among the skipped weeks. In the code (issue #581) it is a link, not a second form: `weeklyPrefillFromSlot` / `makeWeeklyHref` / `parseWeeklyPrefill` (`src/lib/booking-buddy/make-weekly.ts`, pure) carry the prefill in the Games page's search params (`weekly=1`, plus `from`, the original Slot's id), and the form is keyed on it so a second link to the same route seeds it again. `createStandingGame` passes the original to `cover_standing_game_date_with_slot`, which records its date as a `standing_game_weeks` row with no Slot and no `skipped_at`, but only while it is still to come and on the Standing Game's weekday.

Editing a Standing Game (its day, time, division, Intended Org, notes, rotation buffer, reminder offset) only shapes Slots it has not posted yet. A Slot already posted keeps what it was posted with, because people answered for that, and is edited on its own like any other Slot; moving this week's game means skipping it and posting a one-off.

A week can be **skipped** either side of its Slot being posted. Skipping a week that has not been posted yet marks the date on the Standing Game so it is never posted and its Regulars get no Weekly Invite for it; until the date comes it can be put back on. Skipping a week that has been posted deletes that Slot and tells everyone who had answered yes or maybe that it is off; this "it's off" message is particular to a Standing Game, and deleting an ordinary Slot still tells nobody. Either way the date stays skipped, and the following week posts as usual. This is the one respect in which a posted Slot behaves differently for having come from a Standing Game: it cannot be deleted silently, only skipped ("Skip this week" stands in for "Delete game").

In the code (issue #578): a skipped week is a `standing_game_weeks` row with `skipped_at` set and no Slot, so `post_standing_game_week`'s unique key already keeps it from posting. `skip_standing_game_date` / `unskip_standing_game_date` handle weeks not yet posted, `skip_posted_standing_game_week` marks the week and deletes the Slot in one transaction (the same cascade as deleting any Slot). The app reads the yes and maybe answerers first and sends the "it's off" email from `after()` (`game-off-notify.ts`); Guests, "no" answerers and the organizer get nothing, and nobody does once the game has started.

Bookings never carry over between weeks: each week's court is its own Booking, imported or logged as usual, and attaching it stays the organizer's deliberate act. Because an unbooked Slot gets no Reminders, the app points out the obvious match and offers to attach it in one tap, but never attaches on its own (issue #582). A match is a Booking of the organizer's attached to no Slot, at the posted Slot's Intended Org, overlapping its time (touching end to start is not overlap); a Slot that already has a Booking, or has no Intended Org, gets none, and several matches are each offered. It shows as "Attach your 8:00 PM court at X?" on the posted Slot's page and under its Weekly games row, and its button is the ordinary `attachBookingToSlot`. The matcher is `courtMatches` (`src/lib/booking-buddy/court-match.ts`, pure); `listCourtMatches` reads the inputs.

**Ending** a Standing Game stops it posting Slots, for good; there is no restart, only a new Standing Game. Slots it already posted stay as real games (the last one usually should still happen) and can still be skipped one by one; past Slots are untouched. An ended Standing Game leaves the Weekly games section. Since it posts nothing more, its Regulars get no more Weekly Invites.
_Avoid_: Recurring Slot, Series (a Slot never repeats; the Standing Game does)

**Regular**:
A Connection on a Standing Game's own list of the people who are told each time it posts a Slot. The organizer picks the list from their Connections (a Friend Group can fill it in one go) and edits it any time. Anyone who answers "yes" to one of the Standing Game's Slots joins the list on their own; nobody leaves it except by the organizer's hand, so missing a week never drops anyone. Being a Regular decides who is told, not who can see: every Connection with Slot Visibility still sees and can answer the posted Slot, Regular or not. The reverse also holds: a Regular whose Visibility would not show them the organizer's Slots can still open and answer each posted Slot through their own Weekly Invite, the way a Slot Link opens one Slot and nothing else of the organizer's. Adding someone as a Regular is the organizer choosing to share this one game with them. Guests are never Regulars (there is no account to tell).

In the code (issue #579): a `standing_game_regulars` row per (Standing Game, User), owner-managed under RLS. A trigger holds every row to an accepted Connection of the organizer and never the organizer, a trigger on `responses` adds a yes answerer to a posted Slot's Standing Game from whatever path wrote the answer, and a trigger on `connections` takes each party off the other's lists when the Connection ends. The organizer picks the list under "Repeats weekly" on the Post a game form and in the Regulars section of the Standing Game's own page, where a Friend Group's button ticks its members (the group is not linked), and the Weekly games row shows the count. Each time the Standing Game posts a Slot, its Regulars are sent the Weekly Invite (below): `planWeeklyInviteRun` (`src/lib/booking-buddy/weekly-invites.ts`) decides the sends and `weekly_invite_sends` records them once per Slot, User and channel.
_Avoid_: Member, Roster, Invitee (a Slot has no invite list; the Regulars list belongs to the Standing Game)

**Weekly Invite**:
The notification each Regular gets when a Standing Game posts a Slot: email, plus push for a Regular who has push on, sent the moment the Slot is posted. The email carries Yes / Maybe / No links that set that Regular's Response to that one Slot with no sign-in (see [adr/0022-standing-game-invite-answers-need-no-session.md](docs/adr/0022-standing-game-invite-answers-need-no-session.md)). A link opens a page showing the game with that answer preselected, and nothing is recorded until the Regular confirms, so a mail scanner that follows every link answers nothing. The links keep working until the Slot starts, so an answer can be changed; after that, or once the Slot is deleted (a skipped week), or once the Regular stops being the organizer's Connection, the page says the link is done. The page shows only what a Slot Link preview shows of that one game, and it opens whatever the Regular's Visibility of the organizer. The answer is the Regular's own User Response, so a yes keeps them on the Regulars list like any other yes. Governed by its own opt-in preference ("Weekly game invites"), independent of the Reminder's and the Booking Reminder's.
In the code (issue #580): `weekly_invite_links` holds one token per (Slot, Regular), service_role-only like `connection_request_links`, minted by the invite sender (`weekly-invite-sending.ts`) and refused by a trigger for anyone who isn't a Regular. The page is `/answer/<token>?a=yes` (`weeklyInviteAnswerPath`), outside `/booking-buddy` so it needs no session. Its GET reads through `read_weekly_invite`; its Confirm is a Server Action (`answerWeeklyInvite`) calling `answer_weekly_invite`, which takes only the token and the answer, so it can't answer another Slot or as another User. The push opens the same page without a preselected answer. A token dies when its Slot starts, when its Regular stops being the organizer's Connection, or when the organizer takes them off the Regulars list, so an un-ticked Regular's old link can't answer and put them back.
_Avoid_: Invite Link (a User's personal connect URL, unrelated), Reminder (that one is for a confirmed game, close to start)

**Funnel Event**:
One of a small set of Vercel Analytics events marking a User's progress from signup to first value (issue #179): `bb_signup`, `bb_first_facility`, `bb_first_booking`, `bb_first_slot`, `bb_first_friend`, `bb_slot_first_response` (and `bb_onboarding_intent`, once #176 adds the intent choice). Standing Games (#577) add `bb_first_standing_game` (the 0→1 like the rest) and `bb_standing_game_week_posted`, which fires once per week a Standing Game posts (from the cron, creation, or an un-skip) rather than once per User, with `week`, the nth week posted for that Standing Game, so "do Standing Games keep running past week 3" reads off it; the first Slot a new Standing Game posts still counts as `bb_first_slot`. The Weekly Invite (#580) adds `bb_weekly_invite_answered`, which fires on every answer confirmed from an invite link, with `answer` (yes / no / maybe) as its only property. Emitted server-side from `src/lib/booking-buddy/analytics.ts`, and none carries PII. The `bb_first_*` events, `bb_signup` and `bb_slot_first_response` each fire once, on the 0→1 transition (checked against the database, not the client); `bb_standing_game_week_posted` and `bb_weekly_invite_answered` are per-occurrence, which ADR 0014's amendment allows. Read from the Vercel Analytics console, not a dashboard in the app — see [docs/onboarding-funnel.md](docs/onboarding-funnel.md) and [adr/0014-onboarding-funnel-analytics.md](docs/adr/0014-onboarding-funnel-analytics.md).
